Krok 0: První nastavení identity vývojáře

Před prvním commitem je nutné říct Gitu, kdo jste, aby byl autor správně podepsán.

TERMINÁL / BASH Jednorázové nastavení
$git config --global user.name "Jan Novak"
$git config --global user.email "jan.novak@skola.cz"
$git config --global init.defaultBranch main
$git config --list # ověření

Důležité souvislosti

  • Přepínač --global: Nastavení se uloží do domovského adresáře (~/.gitconfig) a platí pro všechny vaše projekty na tomto počítači.
  • E-mail musí odpovídat GitHubu: Pokud použijete stejný e-mail jako na vašem GitHub účtu, GitHub commity automaticky spáruje s vaším profilem.
  • Konec řádků (CRLF vs. LF): Na Windows se doporučuje nastavit git config --global core.autocrlf true.

Scénář 1: Založení nového projektu na disku

Vytvoření prázdného repozitáře a nastavení ignorovaných souborů.

TERMINÁL Inicializace
$mkdir muj-projekt && cd muj-projekt
$git init
# Vytvoří skrytou složku .git
$echo "# Můj projekt" > README.md
$git status

Kriticky důležitý soubor: .gitignore

Soubor, který říká Gitu, které složky a soubory nikdy nesmí commitovat (hesla, dočasné buildy, obrovské knihovny):

node_modules/
.env         # tajné API klíče a hesla!
dist/ / bin/
.DS_Store

Scénář 2: Každodenní cyklus změn (Status → Add → Commit)

Základní rituál, který budete provádět desítkykrát denně.

TERMINÁL Pracovní cyklus
$git status # zkontroluj změny
$git diff # prohlédni řádkové změny
$git add . # přidej vše do Stage
$git commit -m "feat: add user login form"

Konvence commit zpráv (Conventional Commits)

V profesionálních týmech se používají standardizované prefixy:

  • feat: nová funkce pro uživatele
  • fix: oprava existující chyby / bugu
  • docs: změny v dokumentaci či README
  • style: formátování mezer bez změny logiky
  • refactor: úprava kódu bez změny chování

Scénář 3: Propojení s GitHubem a první Push

Odeslání vaší lokální práce do cloudu na GitHub.

TERMINÁL Propojení a odeslání
$git remote add origin https://github.com/uzivatel/repo.git
$git branch -M main
$git push -u origin main
# Každý další push už jen:
$git push

Co tyto příkazy dělají?

  • remote add origin URL: Pojmenuje vzdálený server zkratkou origin a uloží si jeho URL adresu.
  • branch -M main: Přejmenuje výchozí větev na standardní název main.
  • push -u origin main: Odešle commity a parametr -u (upstream) nastaví trvalé sledování větve. Příště stačí napsat jen git push.

Scénář 4: Klonování a stahování práce kolegů

Jak začít pracovat na existujícím projektu z GitHubu.

TERMINÁL Klonování a Pull
$git clone https://github.com/skola/projekt.git
$cd projekt
# Stáhnutí novinek od kolegů:
$git pull

Rozdíl: git fetch vs. git pull

  • git fetch: Zjistí a stáhne nové commity ze vzdáleného serveru do pozadí, ale nesahá na vaše rozpracované soubory. Bezpečné pro inspekci.
  • git pull: Provede fetch a okamžitě automaticky provede merge do vaší aktuální větve.

Scénář 5: Tvorba a přepínání větví (Branching)

Moderní příkaz git switch pro čistou práci s větvemi.

TERMINÁL Správa větví
$git branch # seznam větví
$git switch -c feature/login # vytvoří a přepne
# ... editace souborů a commity ...
$git switch main # zpět na hlavní
$git merge feature/login # sloučení změn

Proč používat git switch místo checkout?

V minulosti příkaz git checkout dělal dvě nesouvisející věci: přepínal větve i zahazoval změny v souborech. Od verze Git 2.23 byl rozdělen na přehledné a bezpečné příkazy:

• git switch (přepínání větví)
• git restore (zahazování změn v souborech)

Scénář 6: Řešení merge konfliktů krok za krokem

Když dva vývojáři přepíší tentýž řádek: jak konflikt bezpečně vyřešit.

SOUBOR V KONFLIKTU Značky Gitu
<<<<<<< HEAD (Vaše aktuální větev)
const port = 3000;
======= (Dělící čára)
const port = 8080;
>>>>>>> feature/login (Slučovaná větev)

Postup vyřešení v 3 krocích:

  1. Ruční úprava v editoru: Rozhodněte, která hodnota má platit (např. const port = 3000;) a odmažte pomocné značky <<<, ===, >>>.
  2. Označení za vyřešené: Napište git add nazev-souboru.js.
  3. Dokončení merge: Zadejte git commit a uložte merge commit.

Scénář 7: Záchranné operace (Stash, Restore, Revert)

Jak napravit chyby a bezpečně odložit rozdělanou práci.

Odložení rozdělané práce (Stash)

Potřebujete rychle opravit bug v jiné větvi, ale máte rozpracované neuložené změny?

$git stash # schová změny do kapsy
$git switch main # oprava
$git switch feature
$git stash pop # vrátí změny zpět

Zahození a vrácení změn

  • git restore soubor.js: Zahodí neuložené změny v souboru a vrátí jej do stavu posledního commitu.
  • git revert <hash>: Bezpečné vrácení: vytvoří nový commit, který přesně obrátí změny starého commitu (vhodné pro veřejný GitHub).

Rychlý tahák nejčastějších příkazů

Všechny klíčové příkazy na jednom přehledném místě.

Příkaz Účel / Význam
git init Inicializuje nový lokální Git repozitář v aktuální složce.
git clone <url> Stáhne existující vzdálený repozitář včetně kompletní historie.
git status Zobrazí stav pracovní zóny, změněné a sledované soubory.
git add . Přidá všechny změny z pracovního adresáře do Staging Area.
git commit -m "zpráva" Uloží připravené změny do historie jako nový trvalý snapshot.
git push Odešle lokální commity do vzdáleného repozitáře (např. na GitHub).
git pull Stáhne a sloučí nejnovější změny ze vzdáleného repozitáře.
git switch -c <vetev> Vytvoří novou větev a okamžitě se do ní přepne.

Shrnutí tématu & Kontrolní otázky

Ověřte si praktickou znalost Git příkazů v terminálu.

Shrnutí klíčových bodů:

Základem práce v Gitu je cyklus git status → git add → git commit. Synchronizace se provádí pomocí git push a git pull. Pro izolaci vývoje slouží větve (git switch -c) a při konfliktech pomáhají vizuální oddělovače a následný merge commit.

1. Jaký je rozdíl mezi příkazy git add a git commit?
git add připravuje vybrané soubory do tzv. Staging Area (ještě nic trvale nezapisuje do historie). git commit vezme vše připravené ve Staging Area a vytvoří trvalý, podepsaný snapshot v historii repozitáře.
2. K čemu slouží soubor .gitignore a proč je nebezpečné commitnout soubor .env?
.gitignore definuje pravidla pro soubory, které Git ignoruje. Soubor .env často obsahuje tajná hesla k databázím či privátní API tokeny. Pokud jej omylem commitnete na veřejný GitHub, útočníci roboticky prohledávající commity mohou během sekund ukrást vaše data nebo zneužít placené služby.
3. Jaký moderní příkaz slouží k vytvoření a okamžitému přepnutí do nové větve?
git switch -c <nazev-vetve> (případně starší zápis git checkout -b <nazev-vetve>).
4. Co provede příkaz git stash a kdy je ideální jej použít?
Dočasně „odloží“ veškeré rozpracované a necommitnuté změny do skrytého zásobníku a uvede pracovní adresář do čistého stavu. Je ideální, když potřebujete narychlo přepnout do jiné větve vyřešit urgentní úkol a nechcete tvořit nedokončený „polovičatý“ commit.
