Proč verzovat? Noční můra bez verzovacího systému

Jak vypadá práce bez Gitu a jakým fatálním chybám verzování předchází.

Světy bez Gitu (ZIP chaos)

  • Ztráta funkčního stavu: Uděláte úpravu, aplikace přestane fungovat a vy už nevíte, co přesně jste před hodinou přepsali.
  • Přepisování práce kolegů: Dva lidé upraví stejný soubor na flashdisku nebo Google Disku – ten, kdo uloží soubor jako druhý, nevratně smaže práci prvního.
  • Nulový kontext: Nikdo netuší, proč v kódu existuje podivná podmínka na řádku 150 a kdo ji tam před půl rokem přidal.

Co přináší systém Git

  • Stroj času: Kdykoli se můžete vrátit k libovolné funkční verzi z minulosti s přesností na jediný řádek.
  • Audit a odpovědnost: U každého řádku víte, kdo jej napsal, kdy a s jakou zprávou vysvětlující důvod.
  • Nezávislé experimentování: Ve větvi můžete vyzkoušet nový nápad; pokud se nepovede, větev jednoduše zahodíte bez rizika pro funkční kód.

Co je Git a jak funguje distribuovaný model?

Vytvořil Linus Torvalds v roce 2005 pro potřeby vývoje jádra operačního systému Linux.

Starý centralizovaný model (SVN, CVS)

Existoval jediný centrální server. Každý vývojář si stáhl pouze aktuální verzi.

Bez internetu nešlo ukládat commity, prohlížet historii ani přepínat větve. Výpadek centrálního serveru ochromil celou firmu.

Moderní distribuovaný model (Git)

Každý klon repozitáře na počítači kteréhokoli vývojáře obsahuje kompletní 100% historii projektu.

Plná práce offline ve vlaku či letadle (commity, větvení, diff). Servery jako GitHub slouží primárně jako spolehlivé synchronizační body.

Anatomie commitu: Snapshot, ne rozdíl

Jak Git vnitřně reprezentuje historii a data vašeho projektu.

Co obsahuje jeden Commit?

  • Kompletní snapshot souborů: Git ukládá stav celého projektu v daný moment (nezměněné soubory sdílí odkazem, šetří místo).
  • Kryptografický Hash (SHA-1 / SHA-256): 40místný unikátní identifikátor (např. 7f3a9e1...), který garantuje integritu. Obsah commitu nelze zpětně zfalšovat.
  • Metadata: Autor, e-mail, datum, čas a smysluplná popisná zpráva (commit message).
  • Rodičovský commit (Parent): Odkaz na předchozí commit – tím vzniká orientovaný acyklický graf historie.

Zlaté pravidlo commitování

Commit by měl být atomický – má představovat jednu logickou, ucelenou a otestovanou změnu (např. „Přidání validace e-mailu ve formuláři“).

Špatně: "zmeny", "oprava", "asdfasdf"
Správně: "Fix: resolve null pointer in user auth"

Tři zóny Gitu: Cesta souboru do repozitáře

Klíč k pochopení toho, proč Git neukládá soubory okamžitě, ale v promyšlených fázích.

1. Zóna

Working Directory

Vaše běžné soubory na pevném disku, které upravujete v editoru. Zde soubory vznikají a mění se.

git status (zobrazí změny)
2. Zóna

Staging Area (Index)

Přípravná zóna pro příští commit. Pečlivě vybíráte pouze ty soubory a řádky, které chcete zahrnout do dalšího snapshotu.

git add index.html
3. Zóna

Git Repository (.git)

Trvalá databáze commitů. Data jsou bezpečně zapsána do historie a opatřena neměnným hashem.

git commit -m "Popis"

Větvení (Branching) a spojování (Merging)

Větve v Gitu jsou lehké, bleskové a umožňují paralelní práci tisíců vývojářů naráz.

Co je to větev (Branch)?

Větev v Gitu je pouhý pohyblivý ukazatel na konkrétní commit. Vytvoření větve nezabírá žádné místo na disku a trvá méně než milisekundu!

  • Hlavní větev (main): Obsahuje stabilní, otestovaný a nasaditelný produkční kód.
  • Vývojové větve (feature/*): Každá nová funkce či oprava se vyvíjí ve vlastní větvi odděleně od ostatních.

Spojování a Merge konflikty

Jakmile je nová funkce hotová, sloučí se zpět do hlavní větve (Merge).

Merge konflikt: Nastane pouze tehdy, když dva vývojáři ve stejné době upravili přesně tytéž řádky ve stejném souboru. Git tehdy zastaví proces a vyzve vývojáře k ručnímu výběru správné varianty.

Git vs. GitHub: Časté nedorozumění

Zásadní rozdíl mezi lokálním nástrojem a cloudovou službou.

Git (Nástroj & Protokol)

  • Příkazový řádkový program běžící lokálně na vašem počítači.
  • Zdarma, open-source, nevyžaduje žádné předplatné ani připojení k internetu.
  • Spravuje commity, historii, větve a slučování v lokální složce .git.

GitHub / GitLab / Bitbucket (Hosting)

  • Webová cloudová služba provozovaná na vzdálených serverech.
  • Uchovává vzdálené kopie vašich repozitářů (Remote repositories).
  • Poskytuje nástroje pro řízení týmu: webové rozhraní pro prohlížení kódu, diskuze, řízení přístupových práv, CI/CD automatizace.

Ekosystém GitHubu: Spolupráce v praxi

Jak moderní technologické firmy a open-source projekty řídí vývoj.

Repozitáře (Public / Private)

Veřejné (otevřené světu pro open source) nebo soukromé projekty s přesně nastavenými právy pro členy týmu.

Issues & Projects

Hlášení chyb, náměty na nové funkce a kanbanové tabule pro přehledné plánování úkolů ve sprintu.

Pull Requests (PR)

Žádost o začlenění kódu z vaší větve. Umožňuje Code Review – kolegové kód projdou, okomentují řádky a schválí sloučení.

Branch Protection

Ochrana produkční větve main: nikdo nesmí posílat změny přímo, sloučení vyžaduje projití testů a schválení seniorním vývojářem.

Automatizace a hosting: GitHub Actions & Pages

Od pushnutí kódu až po živý běžící web na internetu během desítek sekund.

GitHub Actions (CI/CD Pipeline)

Automatizační robot řízený předpisem v .github/workflows/*.yml. Při každém pushi nebo pull requestu v cloudu nastartuje virtuální stroj:

  • Spustí automatické testy a ověří, že kód funguje.
  • Zkontroluje formátování linterem.
  • V případě úspěchu zkompiluje projekt a nasadí jej na server.

GitHub Pages (Statický hosting)

Bezplatný webhosting pro statické weby (HTML, CSS, JS, obrázky) přímo z vybrané větve vašeho repozitáře.

https://vase-jmeno.github.io/nazev-projektu/

Ideální pro školní projekty, portfolio žáka i tyto výukové materiály SPŠ!

Shrnutí tématu & Kontrolní otázky

Ověřte si porozumění principům verzování v Gitu a platformě GitHub.

Shrnutí klíčových bodů:

Git je distribuovaný verzovací systém uchovávající kompletní historii jako graf commitů. Změny putují přes 3 zóny: Working Directory → Staging Area → Repository. Větvení umožňuje bezpečnou paralelní práci a GitHub poskytuje týmové nástroje (Pull Requests, Issues, Actions, Pages).

1. Jaký je rozdíl mezi Staging Area a samotným commitem?
Staging Area (Index) je přípravná plocha, kam pomocí git add přidáváme soubory k zabalení. Samotný commit je až trvale zapsaný neměnný snapshot stavu v databázi repozitáře opatřený autorem a popisem.
2. Proč je Git označován jako „distribuovaný“ verzovací systém?
Protože každý naklonovaný repozitář na lokálním počítači obsahuje plnohodnotnou kopii celé historie a všech větví. Vývojář není závislý na dostupnosti centrálního serveru a může plnohodnotně pracovat offline.
3. Kdy přesně vzniká tzv. Merge konflikt?
Pouze tehdy, pokud v obou slučovaných větvích došlo ke změně na stejném místě (stejných řádcích) stejného souboru a Git nemůže automaticky rozhodnout, která verze má mít přednost.
4. Co je to Pull Request na GitHubu a k čemu slouží Code Review?
Pull Request je formální návrh na začlenění změn z jedné větve do druhé. Code Review je proces, kdy ostatní programátoři kód před sloučením zkontrolují, navrhnou vylepšení a odhalí případné chyby.
