Cesta jednoho kliknutí: Od stisku klávesy Enter k prvním datům

Než se v okně prohlížeče objeví jediný znak HTML, proběhne blesková série síťových operací.

1. URL & DNS Překlad

  • URL Parsing: Prohlížeč rozloží adresu na schéma (https), doménu a cestu.
  • HSTS Preload: Kontrola, zda doména striktně vyžaduje HTTPS bez nešifrovaného HTTP pokusu.
  • DNS Lookup: Prohlížeč zjišťuje IP adresu serveru (např. skolavdf.cz → 81.2.195.118). Kontroluje cache prohlížeče, OS a dotazuje rekurzivní resolver.

2. Spojení TCP & Šifra TLS

  • TCP 3-Way Handshake: Klient a server navážou spolehlivé spojení odesláním paketů SYN → SYN-ACK → ACK (trvá 1 RTT – Round Trip Time).
  • TLS 1.3 Handshake: Výměna kryptografických klíčů pomocí algoritmu Diffie-Hellman, ověření platnosti certifikátu X.509 a zahájení šifrování (v TLS 1.3 trvá pouze 1 RTT).

3. HTTP Request & TTFB

  • Odeslání Requestu: Prohlížeč pošle GET / HTTP/2 s hlavičkami (User-Agent, Accept, Cookies).
  • Server Think Time: Webserver a backend vygenerují data a připraví odpověď.
  • TTFB (Time to First Byte): Klíčová metrika latence – okamžik, kdy do síťové karty klienta dorazí první bajt odpovědi ze serveru.

Proč je latence (RTT) kritičtější než přenosová rychlost (Mbps)?

Než odejde samotný HTTP požadavek, proběhne DNS dotaz (1 RTT), TCP spojení (1 RTT) a TLS handshake (1 RTT). Pokud má uživatel odezvu 60 ms, zpoždění před odesláním prvního bajtu činí minimálně 180 ms i na gigabitové lince!

Critical Rendering Path (CRP) 1: Od bajtů k DOM a CSSOM

Vykreslovací jádro (Blink / Gecko / WebKit) převádí příchozí datový proud do objektových modelů v paměti.

1. Stavba DOM stromu (Inkrementální)

  • Bajty → Znaky → Tokeny → Uzly → DOM: Standardizovaný pětifázový proces převodu surového proudu.
  • Streamované parsování: Prohlížeč nečeká na stažení celého souboru; začíná parsovat první dorazivší pakety okamžitě.
  • Vytváření stromu: Značky <html>, <body> a potomci tvoří hierarchický objektový model přístupný přes JavaScript.

2. Stavba CSSOM (Render-Blocking)

  • Proč CSS blokuje vykreslení? Pokud by prohlížeč vykreslil stránku bez CSS a za chvíli aplikoval styl, stránka by ošklivě blikla (FOUC – Flash of Unstyled Content) a posunula layout.
  • Kompletní strom před kreslením: Na rozdíl od DOMu nemůže být CSSOM stavěn inkrementálně – pozdější pravidlo v CSS může zcela přepsat předchozí pravidla díky kaskádě a specificitě.

Zlaté pravidlo CRP optimalizace

Stylopis umístěný v <head> sice zablokuje zobrazení pixelů (Render-Blocking), ale neblokuje parsování HTML těla níže. Naopak skripty bez atributů blokují kompletně jakékoli další čtení DOMu (Parser-Blocking).

Critical Rendering Path (CRP) 2: Render Tree, Layout a GPU Paint

Jakmile jsou DOM i CSSOM hotové, prohlížeč přistupuje k vizuální konstrukci stránky.

3. Render Tree

Spojení DOMu a stylů z CSSOMu pro všechny viditelné uzly.

  • Vynechává neviditelné elementy (<head>, <script>).
  • Pozor na display: none: Tyto prvky se do Render Tree vůbec nedostanou!
  • Naopak visibility: hidden zabírá prázdné místo, je tedy součástí Render Tree.

4. Layout (Reflow)

Výpočet geometrie a přesných souřadnic každého boxu na stránce.

  • Převádí procenta a relativní jednotky na absolutní pixely podle šířky obrazovky (Viewport).
  • Výpočet toku dokumentu, Flexboxu a CSS Gridu.
  • Výkonnostně drahá operace (tzv. Reflow při dynamické změně velikosti).

5. Paint & Composite

Rasterizace do pixelů a hardwarová akcelerace na GPU.

  • Paint: Vyplnění barev, vykreslení textu, ohraničení a vržených stínů.
  • Composite: Rozdělení na samostatné grafické vrstvy složené grafickou kartou.
  • Animace vlastností transform a opacity neprovádí Layout ani Paint – běží přímo na GPU při 60/120 FPS.

1. Surové bajty & Tokenizace

Síťová vrstva doručí prohlížeči stream surových bajtů přes HTTP odpověď. HTML parser převádí tyto bajty podle kódování (UTF-8) na znaky a následně na lexikální tokeny.

  • Konverze bajtů (např. 0x3C 0x68 0x31...) na znaky <h1>.
  • Tokenizátor rozpoznává počáteční a koncové značky a jejich atributy.
  • Streamované zpracování: parser začíná pracovat ještě před stažením celého HTML!

Blokování parseru skripty: Klasický script vs. Async vs. Defer

JavaScript může přes document.write() nebo DOM API změnit strukturu stránky, proto klasický tag okamžitě zastaví čtení HTML.

<script src="aplikace.js"></script> Parser-Blocking
https://www.skolavdf.cz • Načítání: Klasický <script>
HTML PARSER ZASTAVEN NA ŘÁDKU 14 (ZABLOKOVÁNO)
Prohlížeč musel kompletně přerušit čtení HTML. Stahuje soubor přes síť a ihned jej spouští. Uživatel celou dobu kouká na prázdnou bílou obrazovku!

Co přesně se v prohlížeči odehrává?

  • Parser čte HTML shora dolů a vytváří strom DOM.
  • Jakmile narazí na <script src="...">, okamžitě zastaví stavbu DOM.
  • Odešle síťový požadavek a čeká na stažení celého souboru (stovky ms).
  • Ihned po stažení skript zkompiluje a spustí v hlavním vlákně.
  • Teprve po doběhnutí kódu pokračuje čtení zbývajícího HTML.

Proč je to nejhorší volba?

  • Radikální zpomalení FCP: Uživatel čeká na zobrazení obsahu.
  • Nedostupný DOM: Skript nemůže pracovat s elementy pod sebou (document.getElementById('paticka') vrátí null!).
  • Kdy použít: Dnes prakticky nikdy, kromě drobných synchronních kritických inicializací.
<script async src="mereni-navstevnosti.js"></script> Nezávislý • Neuspořádaný
https://www.skolavdf.cz • Načítání: <script async>
SKRIPT STAŽEN NA POZADÍ → PARSER NÁSILNĚ PŘERUŠEN
Stahování HTML neblokovalo, ale v okamžiku dokončení stahování se parser zastavil, aby se skript ihned spustil. Pořadí spuštění je nepředvídatelné!

Jak funguje asynchronní režim?

  • Skript se stahuje na pozadí, HTML parser mezitím vesele pokračuje.
  • Pozor na zlomový okamžik: Jakmile dorazí poslední bajt, parser se IHNED pozastaví.
  • Skript se okamžitě vykoná a teprve poté se parser probudí.
  • Pořadí běhu je dáno náhodou sítě: kdo dorazí dříve, ten běží první!

Kdy použít a jaká jsou rizika?

  • Kritické riziko: Pokud máte knihovna.js a plugin.js s async, plugin může spadnout na chybu, že knihovna ještě není načtena!
  • Ideální nasazení: Nezávislé skripty 3. stran (Google Analytics, měřicí pixely, reklamy), které nepotřebují DOM ani jiné skripty.
<script defer src="aplikace.js"></script> Doporučený standard • Plynulý
https://www.skolavdf.cz • Načítání: <script defer>
100% PLYNULÉ VYKRESLENÍ BEZ JEDINÉHO PŘERUŠENÍ
HTML parser sestavil celý DOM bez zaváhání. Uživatel má okamžitě před sebou hotovou stránku. Skripty se spustí až nad kompletním stromem v přesném pořadí!

Proč je defer vítězem pro aplikační kód?

  • Stahuje se na pozadí paralelně se čtením HTML.
  • Nikdy nepřeruší parser: HTML parser dokončí celou stránku.
  • Spustí se v momentě, kdy je DOM hotový (před DOMContentLoaded).
  • Přísně garantuje pořadí: Skripty se spustí přesně v tom pořadí, jak jsou zapsány v HTML!

Výhody pro vývojáře i uživatele

  • Rychlé načtení (Optimální FCP/LCP): Uživatel nečeká na JS.
  • Bezpečný přístup k DOM: document.getElementById() vždy najde jakýkoli element kdekoliv na stránce.
  • Moderní moduly: Zápis <script type="module"> se chová automaticky jako defer!

Sestavení stránky z desítek zdrojů & Evoluce protokolů

HTML stránka dnes obsahuje průměrně 70 až 120 dodatečných HTTP požadavků (obrázky, skripty, fonty, ikony).

HTTP/1.1 (1997): Omezení & Fronty

  • Limit 6 spojení na doménu: Prohlížeč smí otevřít maximálně 6 paralelních TCP spojení na stejný hostitel.
  • Head-of-Line (HoL) Blocking: Pokud se první soubor ve spojení zasekne (např. velký skript), všechny ostatní soubory za ním musí čekat ve frontě.
  • Hlavičky bez komprese: Opakované posílání textových Cookies zbytečně plní síť.

HTTP/2 (2015): Multiplexing

  • Jediné TCP spojení: Všechny požadavky i odpovědi protékají jedním TCP spojením.
  • Multiplexing (Toky a rámce): Soubory jsou rozsekány na malé binární rámce (frames) a přenášeny prokládaně bez čekání na dokončení předchozího.
  • Komprese hlaviček (HPACK): Dramatická redukce režie přenosu.

HTTP/3 (2022): QUIC nad UDP

  • Přechod z TCP na UDP: Nahrazuje staré TCP vlastním spolehlivým protokolem QUIC běžícím nad rychlým UDP.
  • Úplná eliminace HoL blockingu: Ztráta jednoho paketu nezpůsobí pozastavení ostatních paralelních proudů dat!
  • 0-RTT Reconnect: Okamžité obnovení spojení při změně sítě (např. přechod z Wi-Fi na mobilní 5G bez výpadku).

Techniky optimalizace a neblokování obsahu

Moderní vývojář aktivně pomáhá prohlížeči prioritizovat a stahovat zdroje nejefektivnějším způsobem.

Resource Hints: Nápovědy pro prohlížeč

  • <link rel="preload" as="font" href="font.woff2"> – Okamžité stažení kritického zdroje s nejvyšší prioritou ještě předtím, než na něj narazí CSS parser.
  • <link rel="preconnect" href="https://fonts.gstatic.com"> – Předem naváže DNS + TCP + TLS spojení na cizí doménu, aby se ušetřila latence 3 RTT při stahování.
  • <link rel="prefetch" href="/dalsi-stranka.html"> – Stažení stránky na pozadí ve volném čase procesoru, pokud je vysoce pravděpodobné, že na ni uživatel klikne.

Líné načítání (Lazy Loading) & Formáty

  • <img loading="lazy" src="foto.webp"> – Nativní odložení stažení obrázku, dokud se uživatel posunem stránky nepřiblíží k jeho zobrazení. Šetří megabajty mobilních dat.
  • Moderní obrazové formáty: WebP a AVIF nabízejí o 30–60 % menší velikost souboru než zastaralý JPEG či PNG při stejné vizuální kvalitě.
  • Webfonty ve formátu WOFF2: Využívají kompresní algoritmus Brotli a jsou až o 30 % menší než formát WOFF.

Optimalizace & DevTools

Atribut defer neblokuje parser, HTTP/2 multiplexuje streamy a záložka Network odhalí úzká hrdla.

1

Proč je CSS považováno za zdroj blokující vykreslení (Render-Blocking) a co by se stalo, kdyby prohlížeč nečekal na CSSOM?

Kdyby prohlížeč vykresloval stránku okamžitě bez staženého CSS, uživatel by viděl čistý nestylovaný text, který by po stažení CSS okamžitě skočil do nového vzhledu (nepříjemné bliknutí FOUC – Flash of Unstyled Content). Prohlížeč proto pozastaví finální fázi kreslení pixelů (Paint), dokud není strom kaskádových pravidel CSSOM kompletní.
2

Jaký je zásadní rozdíl mezi načítáním skriptu pomocí atributu async a atributu defer?

Oba atributy stahují skript na pozadí bez blokace stahování. Rozdíl je v okamžiku spuštění: async spustí skript ihned, jakmile se stáhne, čímž okamžitě pozastaví parsování HTML a nezaručuje pořadí vykonání. Naproti tomu defer počká až na kompletní dokončení stavby stromu DOM (událost DOMContentLoaded), zachovává přesné pořadí skriptů v kódu a nikdy neblokuje vykreslení.
3

Jak vyřešil protokol HTTP/2 hlavní nevýhodu HTTP/1.1 při stahování desítek malých souborů?

V HTTP/1.1 byl prohlížeč limitován maximálně 6 paralelními TCP spojeními na doménu, ostatní soubory čekaly ve frontě (Head-of-Line blocking). HTTP/2 přinesl binární multiplexing: všechna data proudí jediným TCP spojením rozsekána do malých rámců, takže stovky obrázků, stylů a skriptů se mohou stahovat současně bez čekání.
4

Co přesně vyjadřuje metrika TTFB (Time to First Byte) v klientských DevTools a co způsobuje její vysokou hodnotu?

TTFB je doba od odeslání HTTP požadavku klientem do okamžiku, kdy prohlížeč přijme úplně první bajt odpovědi. Zahrnuje síťovou latenci (RTT tam a zpět) a dobu zpracování na serveru (výpočet backendu, pomalé dotazy do databáze). Vysoké TTFB značí pomalý server nebo velkou geografickou vzdálenost bez využití CDN.
