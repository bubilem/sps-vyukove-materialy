Protokol DNS (Domain Name System)

Telefonní seznam celosvětového Internetu • Hierarchický distribuovaný překlad doménových jmen na IP adresy, rekurzivní vs. iterativní dotazy, typy zónových záznamů a zabezpečení DNSSEC.

Účel & Význam

Most mezi lidsky zapamatovatelnými jmény (sps.cz) a číselnými IP adresami, které potřebují routery.

Stromová hierarchie

Kořenová doména (Root .), domény nejvyšší úrovně (TLD .cz, .com) a plně kvalifikovaná jména (FQDN).

Typy záznamů

Zónové záznamy: A (IPv4), AAAA (IPv6), CNAME (alias), MX (pošta), TXT (SPF), PTR a SOA autorita.

Živá simulace

Interaktivní krokování překladu domény od klienta přes kořenový server až po autoritativní odpověď.

Základní poslání

Účel a principy DNS: Telefonní seznam Internetu

Lidé si snadno pamatují jména jako seznam.cz nebo google.com. Síťové přepínače a směrovače však pracují výhradně s číselnými IP adresami.

Proč je DNS distribuovaná databáze?

V počátcích ARPANETu existoval jediný textový soubor HOSTS.TXT spravovaný Stanfordem, který si každý počítač stahoval. S exponenciálním růstem sítě to bylo neudržitelné.

  • Žádný centrální bod: Databáze DNS je rozdělena na tisíce zón po celém světě. Každý správce domény plně ovládá své záznamy.
  • Škálovatelnost a redundance: Dotazy se odbavují z vyrovnávacích pamětí (cache), což zabraňuje přetížení kořenových serverů.

Dva směry překladu

Dopředný překlad (Forward Lookup):

Převod doménového jména na IP adresu (např. sps.cz → 194.108.4.12). Používá se při každém zadání URL do prohlížeče.

Zpětný / Reverzní překlad (Reverse Lookup):

Převod IP adresy na doménové jméno (např. 194.108.4.12 → sps.cz) pomocí PTR záznamu v doméně in-addr.arpa. Slouží k ověření pravosti odesílatelů e-mailů.

DNS Hierarchy

Hierarchická stromová struktura doménových jmen

Jmenný prostor DNS je uspořádán jako obrácený strom. Na samém vrcholu leží neviditelná kořenová tečka (Root).

Root (.)
Kořenová úroveň (Root Level) – reprezentována tečkou na konci FQDN. Celosvětově je spravována 13 jmennými autoritami (A až M), provozovanými přes stovky Anycast serverů.
TLD (.cz, .com)
Domény nejvyšší úrovně (Top-Level Domains) – generické gTLD (.com, .org, .net, .edu) a národní ccTLD (.cz spravovaný sdružením CZ.NIC, .sk, .de).
2. úroveň (sps.cz)
Domény druhé úrovně (Second-Level Domains) – domény registrované konkrétními školami, firmami či jednotlivci (např. sps.cz, cisco.com).
Subdomény
Subdomény a jména hostitelů – libovolně členěné správcem dané domény (např. portal.sps.cz, mail.sps.cz).
Plně kvalifikované jméno (FQDN): Absolutní doménové jméno zakončené tečkou označující kořen, např. portal.sps.cz. (webové prohlížeče koncovou tečku doplňují automaticky).
Infrastruktura DNS

Role a typy DNS serverů v procesu překladu

V DNS hierarchii má každý typ serveru přesně vymezenou úlohu. Žádný server nezná celý Internet.

Rekurzivní Resolver (DNS Klientův agent)

Server poskytovatele připojení (ISP) nebo veřejné služby (Google 8.8.8.8, Cloudflare 1.1.1.1, CZ.NIC 185.43.135.1).

  • Přijme dotaz od počítače klienta a udělá veškerou těžkou práci za něj.
  • Postupně obvolá Root, TLD a autoritativní servery, získá výsledek a vrátí jej klientovi.
  • Ukládá odpovědi do své mezipaměti (Cache) pro bleskovou obsluhu dalších uživatelů.

Autoritativní DNS Server (Držitel pravdy)

Server, který má pro danou doménu nahraný oficiální konfigurační zónový soubor od jejího vlastníka.

  • Zná definitivní a přesné IP adresy (záznamy A, AAAA, MX) pro spravovanou zónu.
  • Není resolverem – neobvolává cizí servery, odpovídá pouze na dotazy týkající se jeho vlastní domény.
Typy dotazů

Proces dotazování: Rekurzivní vs. Iterativní dotaz

Při překladu jména se kombinují dva základní principy dotazování.

Rekurzivní dotaz (Recursive Query)

Klient posílá dotaz svému Resolveru a říká: „Prosím, zjisti mi definitivní IP adresu pro portal.sps.cz. Neodpovídej mi odkazy na jiné servery, chci finální výsledek nebo chybu.“

Klient (notebook) tak nemusí znát strukturu Internetu ani spotřebovávat procesorový výkon na postupné procházení stromu.

Iterativní dotaz (Iterative Query)

Resolver se postupně ptá jednotlivých autorit a ty odpovídají: „Já definitivní IP neznám, ale vím, kdo spravuje další úroveň podrobností – zeptej se tam!“

Root server tak není zahlcován požadavky na konkrétní IP adresy – pouze nasměruje resolver na příslušný TLD server.
Zónové záznamy

Klíčové typy DNS záznamů (Resource Records • RR)

Zónový soubor domény se skládá z typovaných záznamů. Každý záznam slouží k jinému účelu.

A záznam
IPv4 adresa

Převádí doménu na 32bitovou IPv4 (např. 194.108.4.12).

AAAA záznam
IPv6 adresa

Quad-A záznam pro moderní 128bitovou adresu IPv6.

CNAME záznam
Kanonický alias

Alias odkazující na jiné doménové jméno (např. www.sps.cz → sps.cz).

MX záznam
Poštovní server

Mail Exchanger – určuje server pro příjem e-mailů a jeho prioritu.

NS záznam
Jmenný server

Name Server delegující autoritu pro danou zónu.

PTR záznam
Reverzní ukazatel

Zpětné mapování IP adresy na jméno pro antispam.

TXT záznam
Textová data

Textové ověření domény a antispamové záznamy SPF/DKIM.

SOA záznam
Počátek autority

Základní parametry zóny, sériové číslo a časovače.

Port 53

Transportní vrstva DNS: Port 53 nad UDP i TCP

DNS je jedním z mála protokolů, který standardně využívá jak UDP, tak TCP na stejném portu 53.

Port 53 nad UDP (Běžný provoz)

Používá se pro 99 % všech běžných klientských dotazů.

  • Jeden paket s dotazem a jeden paket s odpovědí bez nutnosti navazovat TCP spojení.
  • Maximální původní limit velikosti UDP zprávy byl 512 bajtů (rozšířen mechanismem EDNS0 až na 4096 B).

Port 53 nad TCP (Zónové přenosy a DNSSEC)

TCP se aktivuje ve specifických situacích:

  • Zónové přenosy (AXFR/IXFR): Replikace celého zónového souboru mezi primárním a sekundárním DNS serverem.
  • Odpovědi přesahující limit (Truncation bit TC=1): Pokud se odpověď nevejde do UDP paketu, server vrátí příznak TC a klient dotaz zopakuje přes TCP.
Optimalizace sítě

DNS Caching a hodnota TTL (Time to Live)

Bez mezipaměti (cache) by se světové DNS servery během několika minut zhroutily pod náporem miliard dotazů.

Co znamená TTL u DNS záznamu?

TTL určuje dobu v sekundách, po kterou smí rekurzivní resolver nebo klientský počítač uchovávat odpověď ve své paměti, aniž by se znovu dotazoval autoritativního serveru.

  • Vysoké TTL (např. 86400 s = 24 h): Rychlé načítání, minimální zátěž serveru, ale pomalé šíření případných změn IP adresy.
  • Nízké TTL (např. 300 s = 5 min): Vhodné před plánovanou migrací serveru na novou IP adresu.

Lokální DNS Cache v operačním systému

Každý operační systém si udržuje vlastní lokální vyrovnávací paměť DNS záznamů.

# Zobrazení mezipaměti v OS Windows:
ipconfig /displaydns

# Vymazání mezipaměti (např. po změně webu):
ipconfig /flushdns
Kybernetická bezpečnost

Zabezpečení DNS: Útok Cache Poisoning a obrana DNSSEC

Původní protokol DNS z roku 1983 neobsahuje žádné ověření pravosti. Toho útočníci využívají k podvržení záznamů.

Útok DNS Cache Poisoning (Spoofing)

Útočník podvrhne falešnou odpověď do vyrovnávací paměti rekurzivního resolveru (např. podstrčí IP falešného bankovnictví pro doménu banka.cz). Všichni klienti daného poskytovatele jsou pak přesměrováni na phishingový web!

Obrana: DNSSEC (DNS Security Extensions)

Kryptografické rozšíření DNS, které podepisuje všechny záznamy asymetrickým digitálním podpisem (RRSIG).

  • Resolver si ověří platnost řetězce důvěry (Chain of Trust) od kořene až po konkrétní záznam.
  • Podvržený záznam bez platného podpisu resolver okamžitě zahodí.

Rekapitulace SPŠ

Strukturované shrnutí: Protokol DNS v kostce

Rychlý přehled pro zkoušení a orientaci v protokolu DNS.

Hierarchie a principy

  • Port a transport: Port 53 nad UDP (rychlé dotazy) i TCP (zónové přenosy a DNSSEC).
  • Hierarchie: Root servery (.), TLD (.cz, .com) a autoritativní servery.
  • Dotazování: Klient vysílá rekurzivní dotaz, resolver prochází strom iterativně.
  • Optimalizace: DNS Caching a časovač TTL pro úsporu síťového pásma.

Záznamy a bezpečnost

  • Záznamy: A (IPv4), AAAA (IPv6), CNAME (alias), MX (pošta), TXT (antispam SPF), NS (delegace).
  • Hrozby: DNS Cache Poisoning (podvržení IP do cache).
  • Obrana: DNSSEC – kryptografické podepisování záznamů chránící integritu.
Ověření znalostí

Kontrolní otázky pro upevnění látky

Otestujte své porozumění protokolu DNS.

01. Jaký je rozdíl mezi rekurzivním dotazem a iterativním dotazem v DNS architektuře?
Při rekurzivním dotazu žádá klient svůj resolver o konečnou odpověď (přesnou IP adresu nebo chybu). Resolver pak provede veškeré dohledání za něj. Při iterativním dotazu se resolver ptá nadřazených serverů (Root, TLD) a ty mu odpovídají odkazem na další server, který má podrobnější informace o zóně (např. „Já sps.cz neznám, ale zeptej se na NS serveru pro .cz“).
02. Proč protokol DNS standardně používá port 53 nad UDP, ale v určitých situacích přepíná na TCP?
UDP je preferováno pro běžné dotazy klientů, protože je bleskové a nevyžaduje navazování spojení (jeden dotaz a jedna odpověď). Pokud je však odpověď příliš velká (překročí limit UDP paketu, typicky u velkých kryptografických klíčů DNSSEC), server vrátí příznak Truncated (TC=1) a klient dotaz zopakuje spolehlivě přes TCP. TCP se také povinně používá pro zónové přenosy (AXFR) mezi servery.
03. K čemu slouží hodnota TTL u DNS záznamu a jaký dopad má její nastavení na provoz sítě?
TTL (Time to Live) udává počet sekund, po které smí mezipaměť (resolver i klient) záznam uchovávat bez nového dotazování autoritativního serveru. Vysoké TTL (např. 24 h) šetří šířku pásma a urychluje odezvu, ale zpomaluje šíření změn při přesunu webu na nový server. Nízké TTL (např. 300 s) umožňuje okamžité přepnutí serveru, ale zvyšuje zátěž DNS infrastruktury.
04. V čem spočívá útok DNS Cache Poisoning a jakou ochranu proti němu poskytuje technologie DNSSEC?
Při Cache Poisoningu útočník podvrhne falešnou odpověď do mezipaměti rekurzivního resolveru dříve, než dorazí odpověď od pravého autoritativního serveru. Uživatelé pak při zadání legitimní adresy (např. banky) skončí na falešném serveru. DNSSEC tomu brání tím, že každý zónový záznam je digitálně podepsán asymetrickým klíčem. Resolver podpis ověří proti kořeni a podvržený nepodepsaný záznam okamžitě zahodí.
