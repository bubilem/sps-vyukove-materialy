Protokol HTTP

Bezstavový přenos hypertextu, architektura Klient-Server na portu 80 a způsoby ukládání stavu (Cookies).

Žádosti GET, POST, PUT, DELETE a kompletní přehled odpovědí od 200 OK po 404 a 500 Server Error.

Hypertext • RFC 9110

Účel a vlastnosti protokolu HTTP

HTTP (Hypertext Transfer Protocol) vytvořil Tim Berners-Lee v CERNu v roce 1989. Stal se univerzálním jazykem pro přenos webových stránek, obrázků i datových rozhraní REST API.

Klíčová vlastnost: Bezstavovost (Stateless)

Každý požadavek, který klient odešle, je pro server zcela nezávislý na jakýchkoli předchozích požadavcích. Server si mezi jednotlivými dotazy nepamatuje, kdo jste, ani co jste dělali před 5 sekundami.

Výhoda bezstavovosti: Extrémní škálovatelnost. Server nemusí v paměti držet miliony otevřených uživatelských profilů.

Jak se tedy řeší stav (Přihlášení a nákupní košík)?

Protože samotné HTTP stav nezná, byl vyvinut aplikační mechanismus:

  • HTTP Cookies (Hlavička Set-Cookie): Server po přihlášení pošle klientovi malý identifikátor relace (Session ID). Prohlížeč jej pak automaticky přikládá ke každému dalšímu požadavku.
  • Moderní Web Tokens (JWT): Kryptograficky podepsaný token uchovávaný v paměti aplikace.
Model komunikace

Architektura Klient-Server: Prohlížeč ↔ Webový server

Veškerá webová komunikace se řídí modelem dotaz – odpověď (Request – Response).

Klient (User Agent)

Typicky webový prohlížeč (Chrome, Firefox, Safari) nebo mobilní aplikace:

  • Iniciuje spojení s webovým serverem.
  • Sestaví a odešle HTTP požadavek (Request).
  • Přijme HTML, CSS, JavaScript a multimédia a vykreslí je uživateli na obrazovce.

Webový Server (HTTP Daemon)

Software běžící na serveru (Apache, Nginx, Microsoft IIS, Caddy):

  • Nepřetržitě naslouchá na standardních portech:
    • Port 80 (TCP): Pro nešifrované HTTP.
    • Port 443 (TCP / UDP): Pro zabezpečené HTTPS.
  • Vyhodnotí požadavek a vrátí stavový kód s obsahem (Response).
Syntaxe zpráv

Anatomie zpráv: Struktura požadavku a odpovědi

V původním HTTP/1.1 mají zprávy čistý textový formát s přehlednou strukturou řádků.

  • Hlavičky: Metadata určující hostitele, klientský prohlížeč a formáty.

<!DOCTYPE html><html><body>...</body></html>
  • Stavový řádek: Verze protokolu a trojciferný stavový kód (např. 200 OK).
  • Tělo odpovědi (Body): Samotná data (HTML kód, JSON data nebo binární obrázek).
Status Codes

Přehled HTTP stavových kódů (Status Codes)

Trojciferná čísla vrácená serverem informují klienta o výsledku zpracování požadavku.

2xx Úspěch

200 OK: Vše proběhlo v pořádku.
201 Created: Nový záznam byl vytvořen.
204 No Content: Úspěch bez těla.

3xx Přesměrování

301 Moved Permanently: Trvalý přesun na nové URL.
302 Found: Dočasný přesun.
304 Not Modified: Beze změny (použij cache).

4xx Chyba klienta

400 Bad Request: Chybná syntaxe.
401 Unauthorized: Chybí přihlášení.
403 Forbidden: Zákaz přístupu.
404 Not Found: Soubor neexistuje.

5xx Chyba serveru

500 Internal Error: Pád aplikace.
502 Bad Gateway: Neplatná proxy odpověď.
503 Unavailable: Server přetížen.

Zabezpečení • Port 443

Protokol HTTPS: Kryptografická ochrana webu pomocí TLS

Při obyčejném HTTP putují veškerá data (včetně hesel a čísel platebních karet) v otevřeném textu. Kdokoli na Wi-Fi nebo po trase je může odposlechnout.

Tři pilíře zabezpečení HTTPS

  • 1. Důvěrnost (Šifrování): Nikdo po cestě (ani poskytovatel připojení, ani útočník na kavárenské Wi-Fi) nemůže přečíst obsah přenášených dat.
  • 2. Integrita: Data nelze cestou nepozorovaně pozměnit ani podvrhnout (ochrana proti vkládání škodlivých skriptů).
  • 3. Autentizace serveru: Digitální certifikát X.509 zaručuje, že komunikujete se skutečným webem (např. sps.cz) a ne s podvrženým útočníkem.

Kombinace asymetrické a symetrické šifry

HTTPS spojuje to nejlepší z obou světů kryptografie:

  • Asymetrická šifra (RSA / ECC): Používá se pouze na začátku při TLS Handshaku k bezpečnému vyjednání klíče a ověření certifikátu.
  • Symetrická šifra (AES-GCM / ChaCha20): Extrémně rychlá šifra se společným klíčem, která následně šifruje veškerý objem dat bez ztráty výkonu procesoru.
TLS 1.3 Handshake

Proces TLS Handshake: Jak se naváže šifrované spojení?

Před přenosem prvního bajtu webové stránky proběhne po TCP handshake ještě kryptografický TLS Handshake. V moderním standardu TLS 1.3 stačí k dohodnutí jediný síťový oběh (1-RTT).

Postup výměny v TLS 1.3

  1. 1. Client Hello: Klient posílá podporované verze TLS, seznam šifrovacích algoritmů (Cipher Suites) a svůj parametr pro výměnu klíčů (Diffie-Hellman Key Share).
  2. 2. Server Hello: Server vybere šifru, pošle svůj Key Share, digitální certifikát podepsaný certifikační autoritou (CA) a digitální podpis.
  3. 3. Odvození klíčů: Obě strany nezávisle na sobě matematicky vypočítají naprosto shodný tajný symetrický klíč relace (Session Key).
  4. 4. Finished & Šifrovaná data: Od tohoto okamžiku tečou sítí pouze šifrované bajty!

Role certifikačních autorit (CA)

Jak prohlížeč ví, že server nepodvrhuje útočník?

  • Každý operační systém a prohlížeč má v sobě pevně uložený seznam důvěryhodných kořenových autorit (Root CA).
  • Certifikát webu (např. Let's Encrypt, DigiCert) je kryptograficky podepsán touto autoritou. Pokud podpis nesouhlasí nebo certifikát vypršel, prohlížeč zobrazí červené varování o nebezpečí!

Rekapitulace SPŠ

Strukturované shrnutí: Protokoly HTTP a HTTPS v kostce

Rychlý přehled pro zkoušení a orientaci v protokolech HTTP a HTTPS.

Architektura a syntaxe

  • Bezstavovost: Každý dotaz je nezávislý. Stav je řešen klientskými Cookies a tokeny.
  • Porty: Port 80 pro nešifrované HTTP, Port 443 pro zabezpečené HTTPS.
  • Metody: GET (čtení), POST (vytvoření), PUT (přepsání), DELETE (odstranění).
  • Stavové kódy: 2xx (úspěch), 3xx (přesměrování), 4xx (chyba klienta), 5xx (chyba serveru).

Zabezpečení a evoluce

  • HTTPS = HTTP + TLS: Šifrování obsahu i hlaviček asymetrickou a symetrickou šifrou.
  • Certifikáty: Digitální certifikát X.509 ověřený certifikační autoritou (CA) zaručuje identitu webu.
  • HTTP/2: Multiplexing požadavků v jediném TCP spojení.
  • HTTP/3: Protokol QUIC nad UDP eliminující zpoždění a Head-of-Line blokování.
Ověření znalostí

Kontrolní otázky pro upevnění látky

Otestujte své porozumění webovým protokolům HTTP a HTTPS.

01. Co přesně znamená, že protokol HTTP je „bezstavový“ (Stateless), a jakým způsobem webové aplikace udržují uživatele přihlášeného?
Bezstavovost znamená, že webový server si mezi jednotlivými požadavky nepamatuje žádnou informaci o předchozích krocích klienta. Každý dotaz je vyhodnocen samostatně. Pro udržení přihlášení server po úspěšné autentizaci pošle klientovi v hlavičce Set-Cookie identifikační token (Session ID). Prohlížeč pak tuto Cookie automaticky přikládá ke každému dalšímu dotazu, takže server pozná, o kterého uživatele se jedná.
02. Proč při použití HTTPS využívá vrstva TLS jak asymetrickou, tak symetrickou kryptografii?
Asymetrická kryptografie (dva různé klíče – veřejný a soukromý) řeší bezpečné ověření identity serveru a bezpečnou výměnu tajného klíče přes nedůvěryhodnou síť, ale je výpočetně velmi pomalá. Symetrická kryptografie (jeden společný klíč) je naopak extrémně rychlá a hardwarově akcelerovaná. TLS proto použije asymetrickou šifru pouze při úvodním TLS Handshaku k vyjednání společného klíče a samotná data pak přenáší bleskovou symetrickou šifrou (např. AES-GCM).
03. Jaký je zásadní rozdíl mezi chybovými kódy třídy 4xx a třídy 5xx? Uveďte po jednom příkladu.
Kódy třídy 4xx označují chybu na straně klienta – klient odeslal neplatný požadavek, zadal neexistující URL nebo nemá oprávnění (např. 404 Not Found nebo 403 Forbidden). Kódy třídy 5xx označují chybu na straně serveru – požadavek klienta byl platný, ale server selhal při jeho zpracování, spadl běhový skript nebo je server přetížen (např. 500 Internal Server Error nebo 503 Service Unavailable).
04. V čem spočívá revoluční změna protokolu HTTP/3 oproti HTTP/1.1 a HTTP/2 na transportní vrstvě?
Zatímco HTTP/1.1 i HTTP/2 běžely nad protokolem TCP, HTTP/3 zcela opouští TCP a přechází na protokol QUIC, který běží nad UDP. Tím je odstraněn problém Head-of-Line blokování (kdy ztráta jednoho paketu v TCP zastavila všechny ostatní proudy), TLS 1.3 je integrováno přímo do transportní vrstvy a spojení lze navázat s nulovým zpožděním (0-RTT).
