Protokol DHCP (Dynamic Host Configuration Protocol)

Automatická konfigurace síťových zařízení • Vlastnosti a účel protokolu, proces DORA v detailu, správa doby zápůjčky (Lease Time), DHCP Relay Agent a zabezpečení proti útokům pomocí DHCP Snooping.

Účel & Parametry

Eliminace chyb ruční konfigurace. Předávání IP, masky, brány (Gateway), DNS serverů a doby zápůjčky.

Proces DORA

Čtyři kroky navázání konfigurace: Discover → Offer → Request → Acknowledge na portech UDP 67 a 68.

Správa zápůjčky

Princip Lease Time, automatická obnova zápůjčky (časovače T1 50% a T2 87.5%) a uvolnění adresy (Release).

Relay & Zabezpečení

Směrování přes DHCP Relay Agent (ip helper-address) a obrana přepínačů pomocí DHCP Snooping.

Základní principy

Účel a vlastnosti DHCP: Proč automatická konfigurace?

V malých sítích s 5 počítači lze IP adresy nastavit ručně. V podnikové síti, na školní Wi-Fi nebo v datacentru se stovkami zařízení je manuální konfigurace neudržitelná.

Problémy ruční (statické) konfigurace

  • IP konflikt (Duplicita): Stačí překlep a dva počítače dostanou stejnou IP adresu – obě zařízení přestanou spolehlivě komunikovat.
  • Obrovská administrativní zátěž: Při změně IP adresy DNS serveru nebo výchozí brány by správce musel obcházet stovky počítačů.
  • Plýtvání adresami: Statická adresa zůstává zablokována pro notebook, i když je uživatel doma nebo na služební cestě.

Výhody dynamického protokolu DHCP

  • Plug & Play připojení: Uživatel zapojí kabel nebo se připojí k Wi-Fi a během sekundy je bez jakéhokoli nastavování online.
  • Efektivní recyklace adres: Adresa je zapůjčena pouze po dobu, kdy je zařízení zapnuto. Po odpojení se vrací do fondu pro další klienty.
  • Centrální správa: Změna sítě, brány či DNS serveru se nastaví na jediném místě v DHCP serveru a okamžitě se promítne všem.
DHCP Options

Konfigurační parametry předávané klientovi (DHCP Options)

DHCP server nepřiděluje pouze samotnou IP adresu, ale kompletní sadu síťových parametrů pro plnohodnotný přístup do LAN i Internetu.

Klíčové parametry (Standardní výbava)

  • IP adresa klienta: Unikátní logická adresa z lokálního podsíťového fondu (např. 192.168.1.105).
  • Maska podsítě (Subnet Mask • Option 1): Určuje hranici mezi síťovou částí a hostitelem (např. 255.255.255.0 /24).
  • Výchozí brána (Default Gateway • Option 3): IP adresa lokálního rozhraní routeru (např. 192.168.1.1), kam se posílají pakety do cizích sítí.
  • DNS servery (Domain Name Servers • Option 6): Adresy serverů pro překlad doménových jmen (např. 8.8.8.8, 1.1.1.1).

Doplňkové a podnikové volby (Options)

  • Doba zápůjčky (Lease Time • Option 51): Doba v sekundách, po kterou smí klient adresu používat (např. 86 400 s = 24 hodin).
  • Doménové jméno (Domain Name • Option 15): Přípona lokální domény (např. sps.local).
  • Časové servery (NTP • Option 42): Servery pro synchronizaci času v podnikové síti.
  • TFTP Boot Server (Option 66): IP serveru pro bootování tenkých klientů a instalaci OS po síti (PXE).
L4 • UDP

Transportní vrstva a porty: Proč UDP porty 67 a 68?

DHCP pracuje na transportní vrstvě nad protokolem UDP a vyžaduje přesně definovanou dvojici portů.

Rozdělení portů klient vs. server

Port 67 (UDP) • DHCP Server

Server naslouchá na tomto portu a přijímá zprávy od klientů (DHCPDISCOVER a DHCPREQUEST).

Port 68 (UDP) • DHCP Client

Klientská zařízení naslouchají na portu 68 a přijímají odpovědi od serveru (DHCPOFFER a DHCPACK).

Proč se nepoužívá protokol TCP?

Důvod je zcela fundamentální:

  • Klient zatím NEMÁ IP adresu! Aby bylo možné navázat TCP spojení (Three-Way Handshake), musí obě strany mít platnou IP adresu. Klient však teprve žádá o její přidělení.
  • Nutnost všesměrového vysílání (Broadcast): Klient nezná IP adresu žádného DHCP serveru v síti. Musí proto vyslat zprávu jako Broadcast na adresu 255.255.255.255 se zdrojovou adresou 0.0.0.0. To TCP ze své podstaty neumožňuje.
Jádro protokolu

Čtyři kroky navázání konfigurace: Proces DORA

Výměna zpráv mezi klientem a serverem probíhá v ustáleném cyklu označovaném akronymem D-O-R-A.

D DHCPDISCOVER Klient → Broadcast

Klient volá do sítě: „Je zde nějaký DHCP server? Potřebuji IP adresu!“ (Src: 0.0.0.0, Dst: 255.255.255.255).

O DHCPOFFER Server → Klient

Server odpovídá s nabídkou: „Mám pro tebe IP 192.168.1.105, bránu 192.168.1.1 na 24 hodin.“

R DHCPREQUEST Klient → Broadcast

Klient oznamuje: „Přijímám nabídku od serveru A!“ Broadcastem zároveň dává vědět ostatním serverům, že jejich nabídky odmítá.

A DHCPACK Server → Klient

Server potvrzuje zápis do své tabulky zápůjček: „Hotovo, adresa je tvoje. Můžeš komunikovat.“

Řídicí zprávy

Další zprávy DHCP: Odmítnutí (NAK) a uvolnění (Release)

Kromě základního cyklu DORA definuje protokol DHCP další důležité zprávy pro řešení neplatných stavů a korektní ukončení.

DHCPNAK (Negative Acknowledgment)

Odmítnutí požadavku serverem. Server říká klientovi: „Tuto IP adresu ti nemohu přidělit!“

  • Kdy nastává: Klient se probudí z režimu spánku a žádá o svou starou IP adresu, ale mezitím se přestěhoval do jiné podsítě (např. z domova do školy).
  • Důsledek: Klient musí okamžitě zapomenout svou neplatnou konfiguraci a zahájit proces DORA úplně od začátku novým DHCPDISCOVER.

DHCPRELEASE (Uvolnění adresy)

Dobrovolné vrácení adresy klientem. Klient při korektním odhlášení posílá serveru zprávu unicastem.

  • Příklad v praxi: Příkaz v systému Windows ipconfig /release.
  • Důsledek: Server okamžitě uvolní záznam v tabulce zápůjček a adresa je ihned dostupná pro jiného klienta bez čekání na vypršení časovače Lease Time.
Časovače DHCP

Životní cyklus zápůjčky: Časovače T1 (Obnova) a T2 (Rebind)

Přidělená IP adresa není klientovi dána navždy, ale pouze zapůjčena na stanovenou dobu (Lease Time). Během provozu klient adresu automaticky obnovuje.

Časovač T1: Obnova (Renew)

50 % doby zápůjčky

Při uplynutí 50 % doby pošle klient přímou unicastovou zprávu DHCPREQUEST původnímu serveru. Pokud server odpoví DHCPACK, zápůjčka se obnoví na plných 100 %.

Časovač T2: Znovunavázání (Rebind)

87,5 % doby zápůjčky

Pokud původní server neodpovídá (např. spadl), klient v 87,5 % času vyšle broadcast DHCPREQUEST do celé sítě a žádá libovolný jiný DHCP server o prodloužení.

Expirace zápůjčky

100 % doby zápůjčky

Pokud žádný server neodpověděl a čas vypršel, klient musí okamžitě přestat IP adresu používat. Přechází do stavu INIT a zahajuje nový proces DORA.

Správa adres

Struktura DHCP serveru: Fondy adres, výjimky a rezervace

DHCP server rozděluje IP adresní prostor do logických skupin podle typu připojených zařízení.

Adresní fond (DHCP Pool) a vyloučení

  • DHCP Scope / Pool: Rozsah adres, ze kterých server dynamicky přiděluje (např. 192.168.1.100 až 192.168.1.200).
  • Vyloučené adresy (Exclusions): Rozsah adres vyjmutý z dynamického přidělování, určený pro zařízení s pevnou IP (tiskárny, servery, routery, management switchů – např. .1 až .20).

Statické DHCP rezervace (MAC Mapping)

Kombinace výhod statické i dynamické konfigurace:

  • Správce sváže fyzickou MAC adresu zařízení s konkrétní stálou IP adresou (např. tiskárna s MAC 00:11:22:33:44:55 dostane vždy 192.168.1.20).
  • Tiskárna se stále konfiguruje přes DHCP (automaticky získá bránu a DNS), ale má garantovanou vždy stejnou IP adresu.
Podnikové sítě

DHCP Relay Agent: Jak přeposlat broadcast přes router?

Směrovače (routery) ze své podstaty zastavují všesměrové vysílání (broadcast). Co když máme centrální DHCP server v jiné VLAN nebo v datacentru?

Problém: Broadcast neprojde přes router

Když klient vyšle zprávu DHCPDISCOVER na 255.255.255.255, router na rozhraní tento broadcast zahodí. Museli bychom mít fyzický DHCP server v každé jednotlivé podsíti (VLAN).

Řešení: Cisco ip helper-address

Router funguje jako DHCP Relay Agent:

  • Zachytí klientský broadcast na portu 67.
  • Zabalí jej do směrovatelného Unicast paketu a odešle přímo na IP centrálního DHCP serveru.
  • Příkaz na rozhraní Cisco IOS: Router(config-if)# ip helper-address 10.0.0.50.
Kybernetická bezpečnost

Zabezpečení DHCP: Útoky Rogue Server a ochrana DHCP Snooping

Protože je DHCP protokol založen na důvěře a broadcastu, je oblíbeným cílem útočníků v lokální síti.

Útoky na protokol DHCP

  • Rogue DHCP Server (Falešný server): Útočník zapojí do sítě vlastní DHCP server. Na dotazy DISCOVER odpoví rychleji než legitimní server a podstrčí klientům svou vlastní IP adresu jako Default Gateway (útok Man-in-the-Middle) nebo falešný DNS.
  • DHCP Starvation (Vyhladovění fondu): Útočník chrlí miliony dotazů s podvrženými MAC adresami a vyčerpá všechny volné IP adresy serveru. Legitimní uživatelé se nepřipojí (DoS).

Obrana: DHCP Snooping na přepínači

Bezpečnostní funkce L2 přepínačů (Cisco Catalyst), která rozděluje porty switche:

  • Trusted porty (Důvěryhodné): Porty vedoucí k pravému DHCP serveru či upstream routeru. Zde jsou odpovědi DHCPOFFER a DHCPACK povoleny.
  • Untrusted porty (Nedůvěryhodné): Všechny uživatelské přístupové porty. Pokud z nich dorazí DHCPOFFER, switch paket okamžitě zahodí a port může zablokovat!

Rekapitulace SPŠ

Strukturované shrnutí: Protokol DHCP v kostce

Rychlý přehled pro zkoušení a orientaci v protokolu DHCP.

Klíčové parametry a proces

  • Transport: Protokol UDP, server na portu 67, klient na portu 68.
  • Čtyři kroky DORA: Discover (hledání), Offer (nabídka), Request (žádost), Ack (potvrzení).
  • Předávaná data: IP adresa, maska, výchozí brána, DNS servery, lease time.
  • Časovače: T1 (obnova po 50 % času unicastem), T2 (rebind po 87,5 % broadcastem).

Podniková síť a bezpečnost

  • DHCP Relay Agent: Přeposílá broadcasty přes router jako Unicast (ip helper-address).
  • Statická rezervace: Pevné svázání MAC adresy zařízení se stálou IP adresou z fondu.
  • DHCP Snooping: Ochrana na L2 přepínačích blokující falešné DHCP servery (Rogue DHCP) na nedůvěryhodných portech.
Ověření znalostí

Kontrolní otázky pro upevnění látky

Otestujte své porozumění protokolu DHCP.

01. Proč klient při procesu DORA posílá zprávu DHCPREQUEST jako broadcast, i když již zná IP adresu serveru z nabídky DHCPOFFER?
V síti může být více aktivních DHCP serverů (např. pro redundanci) a klient mohl obdržet více nabídek DHCPOFFER najednou. Tím, že klient odešle DHCPREQUEST všesměrově (broadcast), veřejně oznámí vybraný server a všem ostatním serverům dá najevo, že jejich nabídky nepřijal a mohou své rezervované adresy vrátit zpět do fondu.
02. Kdy a proč nastává situace, že DHCP server odpoví klientovi zprávou DHCPNAK?
Zpráva DHCPNAK (Negative Acknowledgment) nastává tehdy, když klient žádá o prodloužení nebo potvrzení IP adresy, která již v dané síti není platná. Typicky: uživatel měl notebook zapnutý v domácí síti (192.168.1.0/24), uspal jej, přišel do školy (kde je síť 10.0.0.0/8) a probudil jej. Školní DHCP server zjistí, že požadovaná adresa neodpovídá školnímu fondu, odpoví DHCPNAK a donutí klienta zahájit nový proces DORA.
03. K čemu slouží příkaz „ip helper-address“ na Cisco směrovači a jaký problém řeší?
Směrovače standardně nepropouštějí všesměrové vysílání (L2/L3 broadcast). Pokud je centrální DHCP server umístěn v jiné podsíti než klient, zpráva DHCPDISCOVER by k němu nedorazila. Příkaz ip helper-address promění router v DHCP Relay Agent – zachytí klientský broadcast na portu 67, zabalí jej do směrovatelného unicastového paketu a odešle jej na zadanou IP adresu DHCP serveru.
04. V čem spočívá funkce DHCP Snooping na switchi a jak chrání síť před útokem Rogue DHCP Server?
DHCP Snooping rozděluje porty přepínače na důvěryhodné (Trusted – vedoucí k pravému serveru) a nedůvěryhodné (Untrusted – přístupové porty pro běžná PC). Pokud se útočník na uživatelském (untrusted) portu pokusí vysílat serverové odpovědi DHCPOFFER nebo DHCPACK s podvrženou bránou či DNS, přepínač tyto pakety okamžitě zahodí a útok zmaří.
